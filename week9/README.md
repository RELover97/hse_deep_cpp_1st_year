# Рассадка гостей: шаблоны в C++

Представим, что мы собираем друзей на домашний ужин. Нужно знать, кто приглашён, какие места за столом заняты и кто где сидит. Позже понадобится отвечать на вопросы в обе стороны: «На каком месте Аня?» и «Кто сидит на месте № 5?», а также отмечать, кто подтвердил участие.


## 1. Проверка гостя и места

Начнём с двух списков:

```cpp
const std::vector<std::string> guests = {"Аня", "Илья", "Маша"};
const std::vector<int> occupiedSeats = {2, 5};
```

`std::vector<T>` — стандартный контейнер, хранящий последовательность элементов типа `T`. В первом случае элементы — строки, во втором — целые числа.

В `src/main.cpp` есть функции `isInvited` и `isSeatTaken`. Первая проходит по именам и сравнивает очередное имя с искомым; вторая точно так же проходит по номерам мест. Обе возвращают `true`, если нашли совпадение, и `false`, если просмотрели весь список.

Внимательно сравним их *действия*: отличны только тип элемента и тип искомого значения, а сам алгоритм поиска в обоих случаях одинаков.

## 2. Одно действие для разных типов: шаблоны функций

Вместо двух отдельных функций поиска мы хотим написать *один алгоритм*, работающий и со строками, и с числами. Переписывать тела при добавлении нового типа неудобно: исправление ошибки пришлось бы повторять в каждой копии.

В `include/algorithms.hpp` теперь находится:

```cpp
template <typename T>
bool contains(const std::vector<T>& values, const T& wanted) {
    for (const T& value : values) {
        if (value == wanted) {
            return true;
        }
    }
    return false;
}
```

`template <typename T>` объявляет **параметр шаблона** — обозначение типа, который пока неизвестен. Внутри функции `T` используется в трёх местах: тип элементов контейнера, тип искомого значения и тип переменной цикла. Само по себе это описание — ещё не отдельная функция для строк или чисел.

Теперь вызываем:

```cpp
contains(occupiedSeats, 5);                  // T = int
contains(guests, std::string("Аня"));        // T = std::string
```

По типам аргументов компилятор **выводит** `T`, а затем при необходимости создаёт подходящую функцию: `contains<int>` и `contains<std::string>`. Это называется **инстанцированием шаблона** (к нему вернёмся в конце). Тип можно указать явно: `contains<std::string>(guests, "Аня")`. Без явного указания запись `contains(guests, "Аня")` может не пройти: для второго аргумента выводится массив символов, а не `std::string`.

Шаблон не принимает совершенно любые типы автоматически. Функция `contains` требует, чтобы элементы типа `T` можно было сравнивать выражением `value == wanted`. Если такого сравнения нет, при использовании соответствующего `T` компилятор выдаст ошибку.

Это **шаблон функции** (`function template`): тип подставляется в общее описание функции. Вызов конкретной функции после подстановки выглядит и работает как обычный вызов C++.

### Ещё два классических алгоритма

В том же файле расположены `maximum<T>` и `swapValues<T>`. Первая возвращает больший из двух аргументов и потому требует оператора `<`; вторая меняет два объекта местами и требует возможности копирования и присваивания.

```cpp
template <typename T>
void swapValues(T& first, T& second) {
    T temporary = first;
    first = second;
    second = temporary;
}
```

Почему здесь `T&`, а не `T`? При передаче по значению функция обменяла бы только копии, оставив исходные переменные без изменений. `T&` — ссылка на тот же объект, поэтому присваивания меняют аргументы вызывающего кода.

### Почему определения шаблонов находятся в заголовочном файле

Компилятор должен видеть тело шаблона в месте, где создаётся его конкретный вариант. Если оставить в заголовке только объявление, а определение спрятать в отдельно компилируемом `.cpp`, другой файл обычно не сможет инстанцировать новый `T`. Поэтому в этом проекте определения шаблонов лежат в `.hpp`. Это не единственный способ организовать шаблонный код: позднее разберём явное инстанцирование в `.cpp`.

## 3. Хотим знать не только гостя, но и его место

Пока два списка отвечали на независимые вопросы: присутствует ли имя и занят ли номер. Но теперь требуется связь: каждому имени должен соответствовать определённый номер места. Хранить имена и номера в двух независимых векторах неудобно: элементы могут сместиться, и связь между ними потеряется.

В `include/seat_maps.hpp` появляется первый небольшой класс `SeatsByGuest`. В нём хранятся записи:

```cpp
struct Record {
    std::string name;
    int seat;
};
std::vector<Record> records_;
```

Одна запись означает «этот гость сидит на этом месте». `add(name, seat)` просматривает записи, чтобы не добавить одинаковое имя дважды, и при успехе добавляет новую запись. `get(name, seat)` находит гостя и записывает номер в переданный аргумент `seat`:

```cpp
int seat = 0;
if (seats.get("Илья", seat)) {
    std::cout << seat << '\n';
}
```

Параметр `int& seat` — изменяемая ссылка. А возвращаемый `bool` говорит об успешности поиска. Так мы отличаем ситуацию «гостя нет» от найденного номера места, даже если допустимый номер когда-нибудь окажется равным нулю.

На этом этапе класс не защищает от назначения одного места двум разным гостям. Он обеспечивает только уникальность имени. Следующим требованием станет проверка занятости места.

## 4. Требуется поиск в обе стороны

При рассадке нужны два вопроса:

- по имени узнать место — чтобы подсказать гостю, куда идти;
- по номеру узнать имя — чтобы случайно не посадить двух человек на один стул.

В `include/seat_maps.hpp` появляется `GuestsBySeat`. Он устроен почти так же, как `SeatsByGuest`: содержит вектор записей, `add` проверяет, нет ли указанного ключа, а `get` находит значение. Отличается направление соответствия: теперь ключ — `int` (номер места), а значение — `std::string` (имя).

Важно, что ключ — это то, по чему ищем; значение — то, что получаем. Для первой таблицы это «имя → место», для второй — «место → имя».

В `src/main.cpp` мы сначала проверяем, что имя и место ещё не использованы, а затем добавляем запись в обе таблицы. Поскольку после проверок других причин для отказа у этих классов нет, две операции добавления сохраняют согласованность на данном этапе. Изменения уже созданной рассадки здесь не предусмотрены.

Взгляните на реализации классов. Алгоритм один и тот же, но из-за перестановки типов его пришлось написать дважды. Если мы захотим хранить ещё и подтверждения участия — «имя → да/нет», — получится третья копия. Теперь появляется конкретная причина для **шаблона класса**: вынести общую логику таблицы в одну реализацию с параметрами «тип ключа» и «тип значения».

## 5. Одна реализация вместо двух: шаблон класса

В `include/index.hpp` повторяющиеся классы заменены двумя шаблонами:

```cpp
template <typename Key, typename Value>
struct Entry {
    Key key;
    Value value;
};

template <typename Key, typename Value>
class Index {
    // Реализация в include/index.hpp
};
```

`Entry` представляет одну запись, например `Entry<std::string, int>` с ключом «Аня» и значением `2`. Типы `Key` и `Value` не обязаны совпадать, потому что выполняют разные роли. У `Index` есть три метода:

- `add(key, value)` — добавляет пару, если ключ ещё не используется; возвращает `false` при повторном ключе;

- `get(key, result)` — ищет по ключу и записывает найденное значение в `result`; возвращает `false`, если ключа нет;

- `size()` — возвращает число записей.

В `src/main.cpp` обе таблицы теперь создаются из одного шаблона:

```cpp
Index<std::string, int> seatsByGuest; // имя -> номер места
Index<int, std::string> guestsBySeat; // номер места -> имя
```

Это **шаблон класса** (`class template`): `Index` — общее описание, а `Index<std::string, int>` и `Index<int, std::string>` — два разных конкретных типа. В отличие от вызова шаблонной функции, здесь параметры обычно указываем в угловых скобках при создании объекта.

Разберём реализацию `get`:

```cpp
bool get(const Key& key, Value& value) const {
    for (const Entry<Key, Value>& entry : entries_) {
        if (entry.key == key) {
            value = entry.value;
            return true;
        }
    }
    return false;
}
```

`const Key&` означает, что ключ передаётся без копирования и не меняется. `Value&` означает, что найденное значение будет записано в объект вызывающего кода. Заключительное `const` у метода запрещает менять поля самого индекса во время поиска. `entries_` имеет тип `std::vector<Entry<Key, Value>>`, поэтому каждая запись автоматически содержит подходящие типы ключа и значения.

Снова важно: шаблон работает не с любыми типами без условий. У ключа должно быть допустимо сравнение `==`; ключ и значение должны поддерживать используемые операции копирования/присваивания.

## 6. Подтверждения участия: зачем нужна полная специализация

Теперь мы хотим записывать, кто подтвердил участие. Появляется  ещё одно соответствие: имя гостя → `bool`. Создать `Index<std::string, bool>` можно сразу: `Index` не зависит от того, что представляет значение.

Хотим выводить небольшой отчёт. Для чисел и строк достаточно `std::cout << value`; но для `bool` обычный вывод часто даёт `1` или `0`, что менее понятно в строке «Подтвердил участие: ...». Напишем общий компонент форматирования `Printer<T>`:

```cpp
template <typename T>
struct Printer {
    static void print(std::ostream& out, const T& value) {
        out << value;
    }
};
```

Параметр `std::ostream&` позволяет передавать `std::cout` или, позднее, `std::ostringstream` для проверки результата. Метод `print` объявлен `static`, потому что он не хранит состояния: можно писать `Printer<int>::print(std::cout, 5)` без создания объекта `Printer<int>`.

Для `bool` обычная реализация технически работает, но даёт неподходящий формат. Нам требуется ровно один особый случай:

```cpp
template <>
struct Printer<bool> {
    static void print(std::ostream& out, bool value) {
        out << (value ? "да" : "нет");
    }
};
```

Это **полная специализация** (`full specialization`). После `template <>` больше нет неизвестных параметров типов: мы полностью зафиксировали `T = bool`. При вызове `Printer<bool>::print(...)` компилятор использует эту реализацию, а `Printer<int>` или `Printer<std::string>` по-прежнему используют общую.

Обратите внимание: мы не проверяем тип внутри общего `print` и не добавляем `if` на каждый возможный тип. Выбор реализации делается на этапе компиляции по типу. Специализация должна быть объявлена там, где она видна к моменту нужного использования.

У специальных вариантов может быть и совсем другая реализация. Здесь у всех вариантов одинаковый метод `print`, потому что вызывающему коду удобно пользоваться единым интерфейсом.

Чем специализация отличается от обычной перегрузки функции? Здесь мы специализируем класс `Printer<T>`, а не просто добавляем ещё одну свободную функцию с именем `print`.

## 7. Требуется печатать целый список: частичная специализация

До сих пор мы печатали одно число, одну строку или `bool`. Но для отчёта удобно напечатать всех гостей сразу, а рядом — список занятых мест:

```text
Гости: [Аня, Илья]
Занятые места: [2, 5]
```

Стандартный `std::vector<T>` нельзя передать обычному `std::cout << values`: у вектора нет стандартного потокового оператора `<<`. В то же время мы не хотим писать `Printer<std::vector<std::string>>` и `Printer<std::vector<int>>` независимо: в обоих случаях выводим квадратные скобки и запятые, а элементы форматируем уже знакомым способом.

Новая разновидность проблемы: все векторы нужно печатать одинаково, но тип их элементов может быть любым. Для этого в `include/printer.hpp` появляется:

```cpp
template <typename T>
struct Printer<std::vector<T>> {
    static void print(std::ostream& out, const std::vector<T>& values) {
        out << '[';
        for (std::size_t i = 0; i < values.size(); ++i) {
            if (i != 0) {
                out << ", ";
            }
            Printer<T>::print(out, values[i]);
        }
        out << ']';
    }
};
```

Это **частичная специализация** (`partial specialization`): мы зафиксировали форму типа — именно `std::vector<T>`, — но оставили **один неизвестный параметр** `T`. В полной специализации `Printer<bool>` не оставалось ни одного неизвестного типа; здесь `T` определяется из типа конкретного вектора.

Внутри цикла `Printer<T>::print` выбирает нужный способ вывода **каждого элемента**. Для вектора чисел сработает общий `Printer<int>`, для вектора строк — `Printer<std::string>`. Если понадобится вектор векторов целых чисел, тот же приём сработает рекурсивно: внешний `Printer<std::vector<std::vector<int>>>` будет вызывать внутренний `Printer<std::vector<int>>`.

Разница трёх объявлений:

```cpp
template <typename T> struct Printer;                 // общий шаблон
template <> struct Printer<bool>;                    // полная специализация
template <typename T> struct Printer<std::vector<T>>; // частичная
```

При выборе реализации компилятор подбирает применимую, наиболее специализированную форму. Так мы описываем одно правило для **целого семейства типов**, не создавая отдельной копии под каждый конкретный вектор.

Ограничение остаётся честным: если у типа элемента нет подходящего `Printer<T>` и нет оператора `<<` для общего варианта, вывод такого вектора не скомпилируется. Никакой универсальной магии нет.

## 8. Число мест известно заранее: нетиповой параметр шаблона

За нашим столом только шесть стульев. Теперь необходимо ограничить число записей в таблице: при попытке назначить седьмое место программа должна отказать. Ограничение важно для самой рассадки, а не для способа форматирования.

До сих пор параметры `Key` и `Value` обозначали *типы*. Но иногда одна и та же структура отличается значением, известным во время компиляции, например максимально допустимым числом элементов. Изменим объявление индекса:

```cpp
template <typename Key, typename Value, std::size_t Capacity>
class Index {
    static_assert(Capacity > 0, "Index capacity must be positive");
    // ...
};
```

`Capacity` — **нетиповой параметр шаблона** (`non-type template parameter`, NTTP). Он имеет тип `std::size_t` и представляет целочисленное значение, а не тип элемента. `static_assert` проверяет во время компиляции, что ёмкость положительна.

В `add` после проверки на повторный ключ добавлена проверка:

```cpp
if (entries_.size() >= Capacity) {
    return false;
}
entries_.push_back({key, value});
```

Пример использования:

```cpp
constexpr std::size_t tableCapacity = 6;
Index<std::string, int, tableCapacity> seatsByGuest;
```

`constexpr` означает, что значение переменной можно использовать как константное выражение. Обычная переменная, значение которой мы читаем во время выполнения, аргументом такого параметра быть не может:

```cpp
std::size_t n = 6;
// Index<std::string, int, n> wrong; // n не константа времени компиляции
```

`Index<std::string, int, 6>` и `Index<std::string, int, 12>` — разные типы, хотя `Key` и `Value` совпадают. Число `Capacity` входит в полный набор аргументов шаблона.

Важное ограничение нашей реализации: внутри по-прежнему хранится `std::vector`. `Capacity` ограничивает логическое число записей, но не создаёт массив из ровно шести элементов и не гарантирует фиксированный расход памяти. Для физически фиксированной ёмкости понадобилось бы иное хранение, например `std::array`, с дополнительной работой над инициализацией элементов.

Следующий шаг покажет ещё одно следствие параметров шаблонов: при разных наборах параметров компилятору может понадобиться создавать разный машинный код.

## 9. Что компилятор делает с шаблонами: инстанцирование и рост бинарника

Теперь программа использует несколько разновидностей индекса: «имя → место», «место → имя», «имя → подтверждение». Все они написаны как один шаблон `Index`, но конкретные `Key`, `Value` и `Capacity` различны. Что происходит при компиляции?

Когда в коде встречается использование `Index<std::string, int, 16>` и его методов, компилятор может инстанцировать нужные определения для этой комбинации параметров. Для `Index<int, std::string, 16>` нужны другие определения, потому что набор типов другой. Для одинакового набора аргументов не требуется писать новые определения вручную: их описание уже находится в заголовочном файле. При этом компилятор и компоновщик вправе объединять или удалять эквивалентный/неиспользуемый код — количество специализаций не равно автоматически количеству уникальных машинных функций в итоговом файле.

### Небольшой эксперимент

В папке `experiments/` находятся два самостоятельных примера:

- `one.cpp` создаёт и использует только `Index<std::string, int, 16>`;
- `many.cpp` использует пять разных сочетаний аргументов `Index`.

Запустите:

```bash
make sizes
```

`Makefile` собирает оба исходника как объектные файлы (`.o`) и исполняемые программы, используя `-O0 -fno-inline -g0` для более наглядного сравнения. Затем `wc -c` показывает размеры файлов в байтах, а `nm -C` выводит некоторые деманглированные имена символов, содержащие `Index<`.

На Linux или macOS можно отдельно посмотреть:

```bash
nm -C build/many.o | grep 'Index<' 
size build/one build/many
```

В первой команде `nm` выводит символы, `-C` восстанавливает читаемые C++-имена, `grep` оставляет строки с нашим шаблоном. Во второй команде `size` показывает размеры некоторых секций программы, обычно кода и данных. Размер файла на диске и размер выполняемого кода — не одно и то же. Отладочная информация, формат объектного файла, системные библиотеки, оптимизации и настройки компоновщика влияют на результат.

### Почему это важно

Плюс шаблонов — повторное использование одной реализации и проверка типов во время компиляции. Потенциальная цена — дополнительные специализации и увеличение времени компиляции или объёма сгенерированного кода (*code bloat*). Такой рост не гарантирован для каждого шаблона: компилятор может встроить короткие методы, удалить неиспользуемые варианты, а компоновщик — объединить некоторые реализации. Поэтому корректно обсуждать результат конкретного измерения, а не обещать неизбежный рост при каждом новом `T`.

Шаблоны иногда инстанцируют **явно**. Например, при разделении проекта на заголовок и `.cpp` можно определить методы шаблона в `.cpp` и написать там `template class Index<std::string, int, 16>;`. Это попросит компилятор создать указанную специализацию. В других файлах можно объявить `extern template class Index<std::string, int, 16>;`, чтобы не создавать её повторно; для компоновки потребуется объектный файл с явной инстанциацией. Но такой подход заранее ограничивает набор поддерживаемых комбинаций, поэтому в учебном индексе мы оставили определения прямо в заголовке.
