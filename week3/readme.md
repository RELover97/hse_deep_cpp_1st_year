# Проектирование класса с инвариантом

## Постановка задачи

Пусть мы хотим спроектировать в программе электронный кошелёк с лимитом (`Wallet`). Что нам надо знать про объект такого кошелька? 

1) его характеристики:

- баланс (`balance`)
- лимит (`limit`)
- номер кошелька (`id`)

2) что можно делать с таким кошельком?

- положить деньги на него
- снять деньги с него
- узнать баланс
- узнать лимит

3) какой кошелёк считаем валидным, а какой нет?

Если
- `balance` $= 500$,
- `limit` $= 1000$,

то да. 

Если 
- `balance` $= 0$,
- `limit` $= 1000$,
то да. 

Если 
- `balance` $= 1000$,
- `limit` $= 1000$,

то да. 

Если 
- `balance` $= -100$,
- `limit` $= 1000$,

то нет. 

Если 
- `balance` $= 1000$,
- `limit` $= 500$,

то нет. 

Если 
- `balance` $= 500$,
- `limit` $= -1000$,

то нет. 

Итого получаем, что валидный объект кошелька обладает следующими свойствами:

- `limit` $> 0$
- `balance` $\ge 0$
- `balance` $\le$ `limit`
- `id` является уникальным числом и не меняется после создания объекта. 

Совокупность этих свойств образуют **инвариант** нашего типа "кошелёк", то есть выполнение этих свойств наш класс должен гарантировать всегда, пока объект существует.

## Класс или структура

Напишем в `main.cpp` реализацию типа `Wallet`. 

Можно ли тип объявить структурой, а не классом? В случае структуры кто гарантирует соблюдение инварианта?

Отличие класса и структуры.

Какие поля необходимы, чтобы хранить состояние кошелька?

- `balance`
- `limit`
- `id`

Нужны ли ещё поля?

- `is_empty`: нет, так как `balance` $== 0$ отвечает на вопрос

- `is_full`: нет, так как `balance` $==$ `limit` отвечает на этот вопрос

- `remaining_money`: нет, так как `limit` $-$ `balance` отвечает на этот вопрос

Правило: не надо хранить в качестве полей то, что можно вычислить из других полей

## Как работать с объектом класса?

Чтобы гарантировать сохранение инварианта, поля класса надо закрыть (сделать `private`). По умолчанию, в классе поля являются закрытыми. 

Как тогда пользователю кошелька работать с ним? Определить публичный интерфейс (`public`) - методы, доступные пользователю класса. Реализация этого интерфейса осуществляет непосредственно работу с полями классами. Это и есть **инкапсуляция** данных.

## Как создать объект класса

В какой момент появляется объект кошелька? Может ли объект на короткое время находиться в неправильном состоянии?

Объявим конструктор:

`Wallet(int limit);`

Напишем такую реализацию:
```
Wallet(int limit):
{
    limit = limit;
}
```

Что здесь плохо?

- перекрытие имён: где `limit` - член класса - а где - входной аргумент?

Можно задать другое имя : `l`, `_limit`

Можно использовать явно `this`:
```
this->limit = limit;
```
Но это менее предпочтительно.

- Такой конструктор сперва создаёт все поля класса по умолчанию (в них мусор), а потом в поле `limit` копируется значение входного аргумента; то есть делается двойная работа

Это особенно плохо, если у нас есть "тяжеловесные" поля в плане копирования (например, хранится большая строка или выделен большой массив на стеке). 

Хорошим тоном считается янвая инициализация всех полей объекта при его создании, чтобы в них не было мусора. 

Правильно использовать список инициализации:
```
Wallet(int l)
    : id (1),
      balance (0),
      limit(l)
{
    ...
}
```

К тому же если класс хранит в себе константные поля или ссылки на другие типы, то их можно инициализировать только с помощью списка.

Надо ли что писать в теле конструктора?

Если передадим конструктору отрицательный лимит? Объект создаётся, когда тело конструктора завершается, то есть мы получаем объект кошелька с отрицательным лимитом, что нарушает установленный нами инвариант.

Входные данные класса надо валидировать! В C++ для этого есть механизм исключений.

C++ допускает создание объектов класса следующим способом:
```
Wallet w = 1000;
```

Это есть создание с помощью неявного преобразования. Такое поведение чаще нежелательно, только если это не предусмотрено сутью класса (например, таким способом можно создавать объект класса комплексного числа из переданного конструктору вещественного числа как частного случая комплексного). Для запрета такого поведения есть ключевое слово `explicit`.

## Что делать с константными объектами?

С такими объектами мы ничего сейчас сделать не можем, что, в целом правильно, потому что мы не должны их менять по определению. Но какие-то операции над ними всё же допустимы, например, практически все геттеры, как узнать лимит такого кошелька. 

Для этого есть квалификатор const у методов. Вообще, `const` стоит писать у тех методов, которые не меняют состояния объекта. Это также даёт возможность компилятору выполнить. дополнительные оптимизации. 

## Как уничтожать объект

Что должен сделать объект класса в момент уничтожения? Рузрушить свои поля, а это три целочисленных поля типа `int`. Нужно ли нам вручную это уничтожать? Нет, так как это стандартные типы данных, которые компилятор уничтожит сам в момент окончания жизни объекта. Если бы мы владели каким-то ресурсом (например, динамической памятью), то да. В таком случае, либо указываем деструктор по умолчанию, либо не пишем ничего:

`~Wallet() = default;`

По правилу 3 (а вообще 5) если мы сами определили конструктор  не по умолчанию, то должны определить ещё сами оставшиеся методы: copy constructor, destructor (а ещё move constructor, move assignment).

## Статические поля

У всех кошельков должен быть уникальный свой номер. Где хранить номер следующего кошелька, который собираемся создать?
`
class Wallet {
    int id;
    int next_id;
    ...
}
`

Почему это плохо? Потому что у каждого кошелька следующий номер будет свой. Нам нужно иметь общий счётчик на все кошельки. Для этого надо определить статическую перменную-член. Также надо модифицироват конструктор.

Как работать с таким полем? Логически это поле принадлежит не объекту, а самому классу. Чтобы это отразить, опрелеляем статический метод. У таких методов нет указателя `this`, как следствие.

## mutable

Допустим, мы хотим вести служебную статистику обращения к кошельку. Для этого заведём поле `inspection_count_` - количество служебных запросов. Это поле не влияет на логическую константность и целостность объекта, которая определяется словом `const`, а относится чисто к техническим изменениям, которые не нарушают смысловую констаность объекта кошелька.

## CMake проект

Рассмотрим простой вариант CMake проекта, вынеся исходные `cpp` файлы в директорию`src`,  а заголовочные - в `include`. Получается следующая взаимосвязь:

- `wallet` - наша собственная **библиотека**

- `wallet_demo` - программа, которая использует нашу библиотеку (пользователь нашей библиотеки)

Target - сущность сборки, а `target_link_libraries` позволяет задать отношения между таргетами.


Допустим, мы хотим уметь выводить историю транзакций красивым образом вместо нашего примитивного способа `Wallet::print_history`. А кто-то из разработчиков уже написал код для такого красивого форматированного вывода и опубликовал на GitHub, например. Мы, естественно, не хотим писать свою версию, а ради экономии ресурсов хотим использовать готовое решение. Этот сторонний код является **библиотекой**, то есть предназначен для многократного переиспользования другими проектами. Встаёт главный вопрос, а как подключить сторонний код к нашему коду. Более детально:

- где взять эту библиотеку?

- как выразить зависимость нашего кода от этой библиотеки?

Существует библиотека форматированного вывода `fmt` (https://fmt.dev/12.0/). Будем её использовать в нашей программе. 

Сперва просто напишем в коде `wallet.cpp`:
```
#include <fmt/format.h>
```
и воспользуемся функцией `fmt::print` в методе `inspect`.

Соберём проект в его корне
```
cmake -B build -S .
cmake --build build
```
и получим ошибку
```
fatal error: fmt/format.h: No such file or directory
```
потому что у нас в проекте появились **сторонние зависимости** (**3rd-party dependencies / libraries**): `fmt` - внешняя по отношению к нашему проекту библиотека, которую мы используем у себя, а её исходный код находится за пределами нашего проекта. Поэтому надо сказать нашей программе, где найти эту библиотеку и как её использовать.

### FetchContent

В `CMakeLists.txt` добавим строки
```
include(FetchContent)

FetchContent_Declare(
    fmt
    GIT_REPOSITORY https://github.com/fmtlib/fmt.git
    GIT_TAG 12.2.0
)

FetchContent_MakeAvailable(fmt)
```

и потом 

```
target_link_libraries(wallet PRIVATE fmt::fmt)
```

Что здесь происходит: `FetchContent` делает зависимость `fmt` доступной на этапе конфигурации проекта, поэтому этот таргет можно использовать дальше в своём проекте, то есть под капотом:

- конфигурируем cmake проект (первый этап работы cmake)

- `FetchContent`

- скачиваем `fmt`

- добавляем `fmt` в `build`

- появляется таргет `fmt::fmt`

- связываем `fmt` с `wallet`

Теперь у нас зависимости выглядят так: `wallet_demo` -> `wallet` -> `fmt::fmt`, то есть `wallet_demo` транзитивно зависит от `fmt::fmt`. А нужно ли нам в этом случае писать:
```
target_link_libraries(wallet PRIVATE fmt::fmt)
```

Нет: если в `main.cpp` не используется функциональность из `fmt`, то приложение просто зависит от `wallet`, при этом ему не важно, а от чего` в свою очередь` зависит `wallet`. Для указания такой связи между таргетами есть ключевое слово `PRIVATE`, которая говорит о том, что зависимость от `fmt` нужна только `wallet` и не нужна `wallet_demo`.

Попробуем в этом случае в `main.cpp` добавить:
```
#include <fmt/format.h>
...
int main()
{
    ...
    fmt::print("Hello from main\n");
    ...
}
```

и получим знакомую ошибку
```
fatal error: fmt/format.hpp: No such file or directory
```

потому что `wallet_demo` не наследует интерфейс `fmt`.

Чтобы в `main.cpp` можно было использовать `fmt`, надо явно прописать:
```
target_link_libraries(wallet_demo PRIVATE wallet fmt::fmt)
```
