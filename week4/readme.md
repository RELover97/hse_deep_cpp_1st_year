# Семинар "Наследование. Динамический полиморфизм"

## Постановка задачи

У нас есть система финансового анализа. Она получает операции:

- доход
- расход
- перевод

Для каждой операции нужно:

- хранить сумму
- хранить описание
- рассчитывать её влияние на итоговый баланс
- выводить информацию

## Первичное решение

В первом приближении мы захотим написать свой класс `Operation` (см. `main.cpp`). Но в чём тут нюанс: 
для каждой операции тот или иной метод должен работать по-своему, то есть должна быть своя реализация
того или иного метода для той или иной операции. Тут нам помогает один из принципов объектно-ориентированного программирования (в С++, в частности) - наследование, которое выражает отношение между классами "is-a", то есть объект производного класса является объектом базового класса.

## Наследование

Напишем производные классы `Income`, `Expense`, `Transfer` и у каждого напишем свою реализацю метода `print`, которая печатает состояние объекта класса. Обратим внимание, что для доступа к полям базового класса внутри методов производного класса надо объявить эти поля как `protected`.
Также для создания объектов производного класса мы вызываем делегирущий конструктор базового класса `Operation`.

## Общий интерфейс для работы с объектами производного класса

Зачастую нас может интересовать одинаковый сценарий работы с разными объектами - наследниками одного базового класса, например, мы хотим "обойти" все имеющиеся операции в нашей финансовой системе и для каждой из них напечатать информацию на экран, при этом, в каждый момент такого обхода мы должны знать, какую операцию на самом деле мы рассматриваем (income, expense, transfer) и для неё вызвать свою функкциональность для вывода информации на экран. То есть технически мы хотели бы проходить массив объектов класса `Operation`, для каждого объекта вызывать метод `print` и при этом чтобы в моменте у нас вызывалась нужная версия `print` в зависимости от вида операции. 

Попробуем это реализовать. При этом напишем некоторую реализацию `print` у `Operation`.

## Виртуальные функции

Видим, что наша программа для всех видов операций печатает информацию, относящуюся к обобщённой операции, то есть компилятор "не видит", что на самом деле под объектами `Operation` скрываются объекты производных классов. Такое поведение компилятора называется **срезкой / slicing**.

Чтобы изменить его на желаемое, надо объявить в базовом классе хотя бы одну функцию виртуальной.

Видим, что текущая реализация всё равно не работает. Причина в том, что динамический полиморфизм работает, только когда мы работаем с объектами производного класса через указатель или ссылку на базовый класс. Исправим реализацию.

В этот раз у нас корректно выводится информация обо всех операциях, кроме `Transfer`: для неё по-прежнему выводится информация о базовой операции. Причина в том, что мы объявить метод `print` класса `Transfer` константным. В такой ситуации уже не срабатывает переопределение метода `print` базового класса: компилятор рассматривает метод `Transfer::print` как самостоятельный метод, который по имени перекрывает метод `Operation::print`. И такой метод уже не участвует в разрешении вызова виртуальной функции по таблице виртуальных функций, потому что в классе `Transfer` уже нет константного метода `Operation::print`. Собственно, этот метод и будет вызван для объекта `Transfer`.

Такое поведение может стать для нас неприятным сюрпризом и оно чаще нежелательно в рассматриваемом нами сценарии. Мы хотели бы, чтобы компилятор отслеживал подобное поведение и уведомлял нас о его наличии. Такой способ есть - ключевое слово `override`. Каждый метод, который мы хотим переопределить в производном классе, надо помечать как `override`. В этом случае, если мы ошибёмся в сигнатуре метода, компилятор выдаст ошибку:
```
void Transfer::print()’ marked ‘override’, but does not override
```

Раз мы работаем с объектами производного класса через указатели на базовый класс и, как правило, такие объекты существуют в динамической памяти, нам надо освобождать под них память. Опять же, мы хотели бы удалить эти объекты через общий интерфейс, то есть в цикле вызвать `delete` по указателю так, чтобы удалился реальный объект. Напишем реализацию этого и увидим, что не она не работает: каждый раз удаляется только часть производного класса, которая наследуется от базового, то есть происходит утечка памяти под часть, относящуюся только к производному классу. Чтобы исправить это поведение, всегда надо при динамическом полиморфизме делать деструктор базового класса виртуальным. 

Обнаружить отстутствие виртуального деструктора при наследовании от полиморфного класса можно с помощью address санитайзера:
```
g++ -fsanitize=address main.cpp
./a.out
```

## Абстрактные классы

Зачастую нас интересует работа только с объектами производного класса, а базовый класс рассматривается как общий интерфейс для доступа к объектам производных классов. В нашем случае может не иметь особого смысла создание объектов абстрактной Operation: нас интересует работа с конкретными операциями вида Income, Expense, Transfer. Чтобы реализовать такое поведение базового класса, надо объявить его **абстрактным**. Для этого достаточно объявить любую его виртуальную функцию как чистую виртуальную, то есть не имеющую тела. В таком случае мы обязаны переопределить такую функцию в каждом классе-наследнике. Также мы не сможем создавать объекты абстрактного класса, но можем определять указатели на такие объекты и работать через них с объектами производного класса через общий интерфейс абстрактного класса. 

```
g++ -fdump-lang-class -c main.cpp
grep -A5 "Vtable for Operation" main.cpp.001l.class
```

## Умные указатели

Чтобы застраховать себя от ручного управления памятью для реализации динамического полиморфизма, можно использовать умные указатели. Их мы рассмотрим позднее в курсе, сейчас просто принимаем к сведению, что уже написаны классы-обёртки, которые внутри себя осуществляют корректную работу с памятью. 

##  Чтение финансовых данных с разных источников

Откуда брать финансовые данные, чтобы работать с ними? Они могут приходить из любого источника, в общем случае:

- база данных SQL
- Excel файл
- CSV документ
- текстовый документ
- ...

Нам надо написать код, который будет корректно считывать данные из любого источника. Создадим класс `FinancialReport`, который хранит все финансовые операции, и класс `ReportImporter`, который отвечает за формирование объекта класса `FinancialReport` из произвольного источника. Первичная реализация - множество `if-else`, что неудобно поддерживать, когда у нас много источников.

Перепишем наше решение архитектурно: будем использовать специальный паттерн проектирования **strategy**, который в коде выражается абстрактным классом с чистым виртуальным методом чтения данных из источника, который будет переопределяться в классах-наследниках (видах источников данных).

Допишем реализацию класса `FinancialReport`.

Напишем примитивные игрушечные стратегии чтения данных из разных источников (естественно, есть готовые библиотеки, которые реализуют функциональность чтения из разных источников данных, в реальном коде мы их будем подключать и использовать, а сейчас просто пишем заглушки). Важно понимать, что каждая такая стратегия реализует один контракт `IOperationReader::read()`, предоставляем абстрактным классом стратегии. 

Теперь осталось написать класс, который будет работать с произвольной стратегией чтения данных из источника - `ReportImporter`. Такой класс называется **контекстом / context**.

В функции `main` посмотрим, как можно использовать написанную функциональность. То есть мы с помощью объекта контекста можем единообразно использовать разные стратегии чтения данных (то есть читать из разных источников).


# Семинар "RTTI. Множественное наследование"

Сейчас у нас есть общий интерфейс `IOperationReader` с конкретными реализациями `SqlReader`, `ExcelReader` и `DocumentReader`. Есть конктест `ReportImporter`, работающий с общим интерфейсом, который ничего не знает про конкретные реализации. 

Допустим, у нас появилось новое требование:
```
Сотрудник службы поддержки должен уметь запрашивать диагностическую информацию у SQL-reader: состояние соединения, имя базы данных и другую техническую информацию. При этом обычный импорт должен работать для всех readers одинаково.
```

Мы могли бы добавить метод `print_diagnostics()` прямо в `IOperationReader`. Но тогда пришлось бы определять его для всех типов, включая те, для которых такая диагностика бессмысленна или реализуется иначе.

Другой вариант — создать отдельный интерфейс дополнительной возможности:

```
class IReaderDiagnostics {
public:
    virtual ~IReaderDiagnostics() = default;

    virtual void print_diagnostics() const = 0;
};
```

Этот интерфейс описывает не способ чтения данных, а возможность получать диагностическую информацию.

Получается, что каждая конкретная операция является экземпляром класса `IOperationReader` (то есть способом чтения данных об операции) и одновременно должна использовать общий интерфейс `IReaderDiagnostics` для получения диагностической информации об этой операции. Технически это означает множественное наследование. 

Меняем объявление `SqlReader`, а `ExcelReader` и `DocumentReader` оставляем без изменений: они по-прежнему реализуют только `IOperationReader` (см. `main.cpp`). Получим, что `SqlReader` реализует два интерфейса: источника данных и диагностики, то есть объект класса `SqlReader` умеет и читать данные по операции (из SQL базы данных), и предоставлять диагностику. При этом `ReportImporter` всё так же работает только с `IOperationReader` и не зависит от `IReaderDiagnostics`.

Посмотрим на устройство полученного класса `SqlReader` в памяти: напишем функцию `show_base_addresses` (см. `main.cpp`)
и используем её в `main`:
```
SqlReader sql_reader;
show_base_addresses(sql_reader);
```
Видим, что адреса базовых подобъектов разные. 

Возникает вопрос: если у нас есть только `IOperationReader*`, как получить указатель на `IReaderDiagnostics`, не зная заранее, что объект — `SqlReader`?

Здесь мы переходим к **RTTI (Run Time Type Information)** - механизм C++, позволяющий получать информацию о динамическом типе полиморфного объекта во время выполнения и безопасно проверять некоторые преобразования типов (`<typeinfo>`):

- `typeid` — запрос информации о типе;
- `dynamic_cast` — проверяемое преобразование указателя или ссылки.

Напишем функцию `inspect_reader` и используем её (см. `main.cpp`). Мы в момент выполнения программы можем получить информацию о настоящем типе reader'а по ссылке на общий интерфейс `IOperationReader`.

Предположим, нам нужно проверить, является ли reader конкретно SQL-reader. Используем для этого `dynamic_cast` (см. `main.cpp`). Это пример **downcast** — преобразования от указателя на базовый класс к указателю на производный. В отличие от `static_cast`, при таком использовании `dynamic_cast` выполняет проверку типа во время выполнения.

Теперь пусть у нас есть указатель на reader:
```
const IOperationReader* reader = &sql_reader;
```
и мы хотим проверить, а поддерживает ли данный reader интерфейс диагностики? Посмотрим функцию `inspect_diagnostics_support` (см. `main.cpp`). В ней исходный указатель `IOperationReader*` относится к одному базовому подобъекту. Целевой указатель `IReaderDiagnostics*` относится к другому базовому подобъекту. `dynamic_cast` проверяет, можно ли получить целевой интерфейс для объекта, и выполняет необходимое преобразование указателя. Это называется **cross-cast** или поперечным преобразованием.

Напишем теперь финальную обновлённую функцию `insprect_reader`.

Итого:

- `virtual` нужен, когда мы хотим вызвать правильное поведение объекта через общий интерфейс.

- RTTI нужен, когда действительно нужно узнать тип объекта или проверить доступность дополнительной возможности.
