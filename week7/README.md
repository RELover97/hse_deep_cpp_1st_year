# Перегрузка функций и операторов: результаты учебных тестов

## Постановка задачи

Представим, что преподаватель проводит три небольших теста. За каждый тест студент получает некоторое количество баллов — целое число. Мы хотим написать простую консольную программу, которая умеет работать с этими результатами: хранить три числа для одного студента, изменять отдельный результат, вычислять сумму баллов и выводить оценки на экран. Позже программа должна хранить результаты нескольких студентов, чтобы по идентификатору можно было найти нужную запись.

Студенты учатся в группах, а внутри каждой группы имеют порядковые номера. Поэтому одного номера недостаточно: студент № 1 есть и в группе A, и в группе B. Для каждой записи понадобятся два связанных понятия: `Scores` — результаты трёх тестов, и `StudentId` — пара из названия группы и номера студента. Например, наши условные данные могут выглядеть так:

```text
Группа A, студент 1: 1, 3, 5 баллов — всего 9
Группа A, студент 2: 5, 5, 5 баллов — всего 15
Группа B, студент 1: 2, 3, 4 балла — всего 9
```

Мы хотим уметь получать результат студента по паре (группа, номер), просматривать записи в определённом порядке, находить количество наборов баллов, удовлетворяющих заданному порогу, и выводить данные в понятном формате. Мы также хотим складывать два набора результатов поэлементно и умножать все три числа на коэффициент.

## Класс `Scores`

Нам нужно хранить три результата одного студента и уметь получать их сумму. Для этого создадим класс `Scores`: его конструктор принимает три целых числа, а метод `total()` возвращает сумму.

Сразу разделим объявление и реализацию. В `scores.hpp` виден публичный интерфейс `Scores`, а в `scores.cpp` находится код методов. `CMakeLists.txt` собирает `main.cpp` и `scores.cpp` в один исполняемый файл с использованием C++17.

## Один интерфейс `print` для разных типов

Сейчас результат выводится напрямую из `main.cpp`. По мере развития программы нам понадобится печатать не только оценки, но и обычные числа. Необязательно придумывать имена `printInt`, `printDouble` и `printScores`: в C++ можно объявить несколько функций `print`, различающихся параметрами. Добавим в `main.cpp` версии `print(int)`, `print(double)` и `print(const Scores&)`, а затем вызовем их с аргументами соответствующих типов.

Компилятор определяет подходящую перегрузку при компиляции, исходя из аргументов вызова; это не виртуальный вызов и не выбор во время выполнения. Функции `print` размещены в безымянном пространстве имён: они нужны только внутри `main.cpp`. Важно, что разные возвращаемые типы сами по себе не создают разных перегрузок — выбор функции определяется её параметрами.

Посмотрев символы в объектном файле, можно убедиться, что аргументы функций кодируются вместе с их именами (mangling):
```
cmake -B build -S .
cmake --build build
nm build/CMakeFiles/scores.dir/main.cpp.o
nm -C build/CMakeFiles/scores.dir/main.cpp.o
```

## Как компилятор выбирает перегрузку

В простых вызовах `print(7)` и `print(2.5)` тип аргумента точно совпадал с одним из параметров. Теперь попробуем передать `short` и `float`. Мы не добавляем для них новые `print`: компилятор может преобразовать `short` к `int`, а `float` к `double`. В наших примерах это продвижения типов (promotions), которые имеют более высокий приоритет, чем обычные стандартные преобразования.

Но подходящая функция не всегда бывает единственной. Создадим `choose(long)` и `choose(double)`. Для аргумента `42` типа `int` обе функции жизнеспособны, однако преобразования `int → long` и `int → double` имеют одинаковый ранг. Поэтому `choose(42)` не скомпилируется: компилятор не должен угадывать наше намерение. Мы оставим этот вызов в комментарии, а рабочие примеры запишем с `static_cast<long>(42)` и `static_cast<double>(42)`. При чтении этих строк полезно помнить, что возвращаемый тип функции не разрешает неоднозначность; `using Number = int` не создаёт нового типа, а верхнеуровневый `const` у параметра, передаваемого по значению, также не создаёт отдельную перегрузку.


## Делаем доступ к отдельному результату удобнее

До сих пор `Scores` позволял получить лишь общую сумму. Если после проверки теста нужно исправить один результат, хотелось бы написать `first[1] = 8`, как при работе с массивом. Для этого добавим в класс `operator[]`. В отличие от обычной функции, такой оператор позволяет использовать синтаксис индексации, однако определять `operator[]` разрешено только как метод класса.

Одной версии оператора недостаточно. Неконстантному объекту нужна функция, возвращающая `int&`: ссылка позволяет присвоить новое значение элементу. Для `const Scores` введём отдельную перегрузку с `const` после списка параметров, возвращающую `const int&`, чтобы чтение оставалось возможным, а изменение через полученную ссылку — нет.

## Складываем результаты, не дублируя логику

Следующая естественная операция — сложить результаты двух объектов `Scores` поэлементно. При этом нужно различать две ситуации: `first += second` должен изменить `first`, а выражение `first + second` — вернуть новый объект, не меняя аргументы. Начнём с метода `operator+=`, который прибавляет элементы другого объекта к закрытому массиву и возвращает `Scores&`.

Теперь реализация бинарного `operator+` становится короткой: свободная функция получает левый операнд по значению, вызывает для этой копии `+=` и возвращает её. Вся арифметика остаётся в одном месте; если способ сложения изменится, не придётся исправлять два независимых алгоритма. Обратите внимание на различие возвращаемых типов: в `+=` выражение `return *this;` безопасно возвращает ссылку на существующий объект и позволяет писать цепочки присваиваний. А результат `+` нужно вернуть по значению: ссылка на его локальную копию после выхода из функции стала бы висячей.

## Поддерживаем обе формы умножения на число

После сложения полезно научиться умножать каждый результат на целое число. По аналогии реализуем метод `operator*=`, изменяющий объект, и свободный `operator*(Scores, int)`, создающий новый результат с помощью `*=`. Но математическую запись обычно хочется использовать в обоих направлениях: не только `scores * 2`, но и `2 * scores`. Поэтому добавим вторую свободную перегрузку `operator*(int, Scores)`.

Этот выбор связан с устройством операторов-методов. Если бы мы определили `operator*` только внутри `Scores`, слева от знака обязательно стоял бы объект `Scores`: у встроенного `int` нет подходящего метода. Свободная функция позволяет явно описать оба порядка операндов, не повторяя цикл умножения. При этом перегрузка не изменяет ни число операндов, ни приоритет `*` в выражениях. В нашем учебном коде арифметика остаётся целочисленной и не проверяет переполнение `int`; при разработке реальной системы такие ограничения потребовали бы отдельного решения.


## Учим `Scores` выводиться в поток

Пока мы печатали либо сумму результатов, либо заранее подготовленный текст. Гораздо удобнее видеть весь объект целиком: `std::cout << scores`. Для этого реализуем `operator<<(std::ostream&, const Scores&)`, который выводит три элемента в виде `[4, 6, 8]`. Слева от `<<` находится поток, а не объект `Scores`, поэтому сделать такой оператор методом `Scores` нельзя: он должен быть свободной функцией.

Мы не хотим открывать массив `values_` всем внешним функциям только ради печати. Вместо этого объявим конкретный оператор как `friend` внутри `Scores`, а его определение поместим в `scores.cpp`. Слово `friend` даёт функции доступ к закрытым данным, но не превращает её в метод. Первый параметр — неконстантная ссылка на поток, поскольку вывод меняет состояние потока; второй — `const Scores&`, поскольку сам объект не меняется. Возвращаем `std::ostream&`, чтобы работала цепочка `std::cout << first << second`. Обратите внимание, что функция объявлена в глобальном пространстве имён и может находиться при записи оператора благодаря поиску по типам аргументов (ADL); к этому механизму мы ещё вернёмся.


## Как увидеть перегруженные операторы в машинном коде (Linux x86-64)

После появления `operator+=`, `operator+`, `operator*` и `operator<<` интересно проверить, что оператор в C++ — это функция, которую компилятор кодирует обычным машинным кодом. Соберём проект с отладочными символами и без оптимизации, чтобы отдельные функции было проще найти.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS_DEBUG='-O0 -g3 -fno-inline'
cmake --build build
```

Начнём с таблицы символов объектного файла, который получился из `scores.cpp`:

```bash
nm -C ./build/CMakeFiles/scores.dir/scores.cpp.o | grep 'operator'
```

Ключ `-C` деманглирует имена (name demangling): мы увидим знакомые обозначения `Scores::operator+=`, `Scores::operator[]`, `operator+`, `operator*`, `operator<<`. Без `-C` компиляторские имена выглядят как `_ZN6ScorespLERKS_` (точный вид зависит от сигнатуры и компилятора). 

При наличии GDB можно остановиться внутри метода и разобрать его инструкции:

```bash
gdb -q ./build/scores
```

```gdb
(gdb) break 'Scores::operator+=(Scores const&)'
(gdb) run
(gdb) info args
(gdb) info registers rdi rsi
(gdb) disassemble /m
(gdb) quit
```

`break` остановит программу перед выполнением оператора; `disassemble /m` покажет машинные инструкции вместе со строками исходника. При сборке с оптимизацией (`-O2`) компилятор может встроить некоторые вызовы и отдельный переход к оператору будет не виден: это не означает, что оператор перестал существовать на уровне языка.

## Добавляем идентификатор студента

Теперь у нас есть удобный тип для трёх оценок, но непонятно, как связать результат с конкретным студентом. Обычного числового номера недостаточно: одинаковые номера могут встретиться в разных группах. Поэтому создадим в `student_id.hpp` простую структуру `StudentId` из двух полей — `group` и `number`. Такая пара будет служить ключом при хранении результатов многих студентов.

Чтобы можно было сравнивать эти ключи и выводить их, определим `operator==`, `operator<` и `operator<<`. Равенство требует совпадения обоих полей. Порядок построим через `std::tie(group, number)`: сначала сравнивается группа, а при совпадении групп — номер. Такой лексикографический порядок удовлетворяет требованиям строгого слабого порядка: в частности, `a < a` всегда ложно. Три оператора определены прямо в `friend`-объявлениях структуры. Это свободные функции, хотя их тела написаны внутри `StudentId`; такой способ называют hidden friend. Найти их при вызове помогает ADL.

## Храним результаты в ассоциативном массиве

Когда ключ и значение готовы, их можно объединить в ассоциативный контейнер `std::map<StudentId, Scores>`. Теперь мы добавляем запись вместе с идентификатором студента, обходим сохранённые записи и запрашиваем результат по заданному ключу. Поскольку `std::map` поддерживает ключи в порядке компаратора, при обычном `std::map<StudentId, Scores>` мы увидим группы по алфавиту, а внутри группы — номера по возрастанию.

Для работы `std::map` важен не `operator==`, а упорядочивающее сравнение (здесь — `operator<` через `std::less<StudentId>`). Контейнер считает два ключа эквивалентными, если ни один не меньше другого. Поэтому корректность выбранного строгого слабого порядка напрямую влияет на поиск и вставку. Мы используем `emplace` для добавления записей и `at` для чтения: `at` не создаёт новую запись и бросает `std::out_of_range`, если ключ не найден. В отличие от него, `map::operator[]` при отсутствии ключа должен создать значение по умолчанию; наш `Scores` не имеет конструктора без аргументов, поэтому здесь такой способ не подходит.


## Меняем порядок ключей отдельным функтором

По умолчанию `StudentId` сравнивается сначала по группе. А если в другой части программы удобнее просматривать студентов сначала по номеру, а только затем по группе? Изменять `operator<` ради одного контейнера было бы неправильно: мы тем самым поменяли бы поведение всех существующих `std::map<StudentId, ...>`. Вместо этого создадим тип `ByNumber` с методом `operator()(const StudentId&, const StudentId&) const` и передадим его третьим аргументом шаблона `std::map<StudentId, Scores, ByNumber>`.

Объект класса, который можно вызвать как функцию, называется функтором. Контейнер создаёт и использует такой объект для сравнения ключей, а `StudentId` при этом остаётся неизменным. В реализации `ByNumber` сравниваются номер, затем группа — по-прежнему оба поля. Если учитывать только номер, студенты из разных групп с одним номером станут эквивалентными ключами для этой `map`, и добавить их как две независимые записи не получится. Поэтому новый компаратор обязан сохранять строгий слабый порядок и отражать именно ту эквивалентность ключей, которую мы хотим получить.


## Используем функтор как настраиваемый предикат

Мы уже использовали `operator()` для изменения порядка в контейнере. Тот же механизм подходит и для алгоритмов. Допустим, требуется посчитать, сколько наборов оценок имеют суммарный результат не ниже заданного порога. Вместо отдельной функции для каждого порога создадим `AtLeastTotal`, который хранит целое поле `minimum` и возвращает из `operator()(const Scores&) const` результат сравнения с `scores.total()`.

Далее передадим `AtLeastTotal{15}` в `std::count_if`. Алгоритм не знает о том, что такое оценки, и просто вызывает предоставленный предикат для каждого элемента. Порог хранится **внутри объекта**, поэтому два экземпляра одного функтора могут проверять разные условия. Метод `operator()` здесь константный: проверка не изменяет ни оценки, ни порог. Обратите также внимание, что `std::count_if` принимает предикат по значению и может скопировать его; эта деталь имеет значение для функторов с изменяемым внутренним состоянием. Лямбда-выражения основаны на похожем механизме, но явный класс позволяет лучше увидеть его устройство.


## Переходим к хэш-таблице с собственным ключом

`std::map` поддерживает отсортированные ключи, но не во всех случаях нам нужен упорядоченный обход. Для поиска по идентификатору можно использовать `std::unordered_map<StudentId, Scores, StudentHash>`. В отличие от `map`, хэш-таблица определяет место хранения по хэш-значению. Стандартная библиотека не знает, как хэшировать наш составной `StudentId`, поэтому мы добавим функтор `StudentHash` с `operator()(const StudentId&) const noexcept`, возвращающим `size_t`.

Хэшер сначала получает значения `std::hash` для `group` и `number`, а затем смешивает их. Учитывать нужно оба поля: ведь и `operator==` считает их частью идентичности ключа. Основное требование состоит в том, что равные ключи обязаны давать одинаковые хэши; разные ключи при этом могут иметь одинаковый хэш, и такие коллизии допустимы. Внутри подходящей корзины контейнер различает ключи по равенству — в нашем случае через `operator==`, используемый стандартным `std::equal_to<StudentId>`. В `unordered_map` нельзя полагаться на порядок обхода, а конкретное численное значение хэша не следует использовать как постоянный идентификатор студента.
