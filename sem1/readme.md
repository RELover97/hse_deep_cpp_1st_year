Проект "Анализатор логов"

Идея: написать консольную утилиту, которая читает лог-файл, например, веб-сервера, 
и выдаёт статистику (общее число запросов, число успешных запросов и тд)

Цель - разобрать этапы компиляции С++.

1. Препроцессинг

`g++ -E main.cpp -o main.i`

Посмотреть первые 30 строк файла `main.i`:
`head -n 30 main.i`

Посчитать число строк в файлах:
`wc -l main.cpp main.i`

Добавим  макрос `#define` в `main.cpp`

Выполниим этап препроцессинга и в полученном файле найдём слова `VERSION` и `version`:

`g++ -E main.cpp | grep VERSION`

`g++ -E main.cpp | grep "version"`

Видим, что раскрытие макросов происходит на этапе препроцессинга

2. Компиляция

Единица трансляции / Translation unit = cpp файл + включённые в него hpp файлы

Единицы трансляции компилируются независимо!

Получить из cpp файла объектный файл `.o`:
`g++ -c main.cpp -o main.o`
`g++ -c parser.cpp -o parser.o`

Обратим внимание, что реализаций `parse_line` и `calculate statistics` в `main.cpp` нет,
но компилятор уже может обрабоать `main.cpp` и создать единицу трансляции для него.

Это возможно благодаря наличию объявлений (declarations) этих функций в hpp файлах, которых достаточно для этапа компиляции. 

Сами реализации (definitions) нужны будут уже на этапе линковки (likage).

Поменяем сигнатуру `parse_line` в hpp файле и скомпилируем `main.cpp`

Получим ошибку несоответствия вызова функции её сигнатуре.

3. Assembly / Ассемблирование

Получить из исходного файла файл на языке ассемблера:
`g++ -S main.cpp -o main.s` - синтаксис ассемблера AT&T
`g++ -S main.cpp -masm=intel -o main.s` - синтаксис ассемблера Intel (проще читать)

4. Compiler optimization

Создадим вне проекта `square.cpp` и скомпилируем его до объектных файлов с разными опциями оптимизации кода:
её отсутствием (`O0`) и 2м уровнем (`O2`)

`g++ -S -O0 square.cpp -masm=intel -o square_O0.s`

`g++ -S -O2 square.cpp -masm=intel -o square_O2.s`

Посмотрим отличие ассемблерного кода:
`diff -u square_O0.s square_O2.s`

5. Assembly

Ассемблерный файл также компилируется (ассемблируется) до объектного:

`g++ -c main.s -o main.o`
`g++ -c parser.s -o parser.o`

`.o` - object file - представляет собой бинарный файл, который содержит почти исполняемый код (остаётся линковщику вставит адреса вместо символов, определённых в других единицах трансляции, а также стартовый код для запуска `main`)

Можно посмотреть содержимое бинарного файла и дизассемблированный код (код на языке ассемблера, восстановленный по двоичному коду) объектного файла:

`objdump -d main.o`

`g++ main.o -o main`

`./main`

See error from ld `undefined reference`

6. Linkage

Каждый cpp файл надо скомпилировать в объектный файл и это происходит не зависимо друг от друга

`g++ -c main.cpp -o main.o`

`g++ -c parser.cpp -o parser.o`

`g++ -c stats.cpp -o stats.o`

Собираем из всех объектных файлов исполняемый файл `logs_analyzer`:
`g++ main.o parser.o stats.o -o logs_analyzer`

Запускаем на исполнение и видим, что программе нужен входной аргумент - имя файла с логами для анализа:

`./logs_analyzer`

`./logs_analyzer access.log`

Попробуем удалить объектный файл `parser.o` и собрать программу из оставшихся:

`rm parser.o`
`g++ main.o stats.o -o logs_analyzer`

При запуске получим underfined reference error:
`./logs_analyzer`

Можно посмотреть таблицу символов объектного файла:

`nm main.o`

U = undefined: символ используется в объектном файле, но определения нет
T = символ определён в объектном файле 

В нашем случае для `main.o`: 

U:
- `parse_line`
- `calculate_statistics`

T:
- `main`

7. Реорганизуем проект

Когда файлов становится много, то для структуризации проекта и удобства работы с ним принято группировать определнные виды файлов. 

- `src` - файлы`.cpp`
- `include` - файлы `.hpp`

При такой организации файлов если попробовать скомпилировать проект, то получим ошибку, что препроцессор не может найти заголовочные файлы `stats.hpp` и `parser.hpp`, которые включаются в `main.cpp`:

`g++ main.cpp src/parser.cpp src/stats.cpp -o main`

Это связано с тем, что заголовочные файлы в `include` директивах ищутся по текущему пути относительно файла, в который они включаются; если мы перемещаем hpp файлы в incude директорию, тогда в include директивах надо писать путь к этим файлам: `include/parser.hpp` и `include/stats.hpp`. Так можно делать, но неудобно, особенно если включается много hpp файлов и они вложены глубоко. 
Проще использовать флаг компилятора `-I` и аргумент к нему - путь до hpp файлов; в таком случае компилятор будет знать, где искать все hpp файлы и тогда в `include` директивах достаточно будет писать только имя hpp файла:

`g++ -c main.cpp -I include -o main.o`

`g++ -c src/parser.cpp -I include -o parser.o`

`g++ -c src/stats.cpp -I include -o stats.o`

`g++ main.o parser.o stats.o -o logs_analyzer`

А если у нас на 2 hpp / cpp файла, а 22? 122? 1000? Писать вручную все эти командны совсем не хочетсяя да и в случае ошибки искать её можно часами. 

А ещё мы хотим, чтобы наш проект работал на разных ОС, архитектурах, то есть был переносимым.

8. Cmake

Утилита, которая позволяет автоматизировать процесс сборки

В корне проекта создаём `CMakeLists.txt`

Создадим минимальный файл:

`cmake_minimum_required` - минимальная версия cmake, с которой можно запускать проект

`project` - описание проекта

`add_executable` - создать исполняемый target 

У target есть свойства:
- имя
- тип
- исходные файлы
- include directories
- compile options
- dependencies
- link libraries

То есть мы говорим, как получить исполняемый файл, из каких файлов надо собрать target.

Этапы работы cmake:

1) конфигурирование:

- чтение дерева исходного кода (source tree)
- подготовка дерева сборки (build tree)
- сбор сведений об архитектуре, доступных компиляторах, линковщиках
- разбор `CMakeLists.txt`
- создание `CMakeCache.txt`, временных файлов, журналов

`cmake -S . -B build`

2) сборка проекта

- создание сборочной системы - специального конфигурационного файла для других элементов сборки (например, `Makefile` для GNU Make или Ninja)

- запуск компилятора, линковщика

`cmake --build build`

`cmake --build build --verbose`

3) запуск проекта

`./build/logs_analyzer`

Рекомендуется использовать out-of-source build, то есть дерево сборки должно быть вынесено отдельно от дерева исходного кода

Теперь мы хотим отделить бизнес-логику от CLI.

`add_library`

Теперь есть два таргета:
- `logs_analyzer`
- `logs_analyzer_core`

Теперь надо сообщить `logs_analyzer` о `logs_analyzer_core`

`target_link_libraries`

То есть это по сути линковка двух объектных файлов

`logs_analyzer` использует `logs_analyzer_core`, но потребители `logs_analyzer` не наследуют эту зависимость как свою публичную зависимость.

Propagation механики:

- `PRIVATE`
- `PUBLIC`
- `INTERFACE`

Про это будет отдельный семинар

Добавим include директорию

`target_include_directories`

`PUBLIC` = header-файлы библиотеки являются частью интерфейса `logs_analyzer_core`.

Теперь при компиляции не нужно указывать `-I include`
